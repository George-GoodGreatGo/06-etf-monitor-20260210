# 980081（国证价值100）PE“历史基线 + 官网日更”方案评估与实施计划

## Summary

* 结论：你的思路“历史数据用历史文件，新数据每日查询记录”是可行且推荐的，但要补上**融合规则与可观测性**，否则会出现口径漂移或重复写入问题。

* 推荐落地：采用“**历史基线导入 + 交易日21:00官网增量抓取 + 冲突日新值覆盖历史 + 失败不发布沿用上个可见run**”。

* 适配目标：替换当前 `980081` 在 `valueTiming` 中不稳定的 `public_api_then_etf` 单点链路，提升 nightly 发布成功率，同时保持可回溯。

## Current State Analysis

* 已有实现现状（代码）：

  * `server/lib/valueTiming.ts` 对 `980081` 的 PE 来源是 `public_api_then_etf`：

    * 先走 `runAkshare(... index-valuation ...)`；

    * 无数据再走 ETF `159263` 兜底；

    * 这条链路近期多次导致 `pe=0` 进而触发覆盖率失败，整次 run 不发布。

  * `server/scripts/refreshValueTimingSnapshots.ts` 已使用 run 原子发布，且对 `980081` 设较低覆盖阈值；但当 PE 彻底缺失时仍会失败（这是合理风控）。

* 参考方法论文档（已读取）给出的关键事实：

  * 官网 `index/running?type=1` 提供最新 `peDynamic`（不带历史序列）；

  * 官网 `getMarketDay?codesValue=980081` 提供 `lastMarketDay`，可作为交易日归因；

  * 因此官网适合“日更快照”，不适合“历史回补”。

* 你提供的数据资产：

  * `参考文档_for_references/价值100-pettm-2026-04-15.xlsx` 可作为历史基线；

  * 列映射已确认采用“代码自动识别”（日期列候选 + PE列候选）。

## 方案评估

* 方案A（仅官网日更，不用历史基线）：不推荐。无法补齐历史，分位与回测稳定性差。

* 方案B（仅历史文件，不做日更）：不推荐。数据会停止更新，实时性缺失。

* 方案C（历史基线 + 官网日更融合）：推荐。

  * 优点：历史完整 + 新值持续更新 + 可审计；

  * 风险：同日冲突、节假日重复写、官网临时不可用；

  * 对策：你已决策

    * 冲突日：新值覆盖历史；

    * 日更失败：不发布新 run，沿用上个可见 run；

    * 日更时间：晚间 21:00 统一窗口。

## Proposed Changes

### 1) 新增 980081 PE 融合服务（历史+增量）

* 修改文件：`server/lib/valueTiming.ts`

* 变更内容：

  * 新增 `fetchCnindex980081LatestPeWithTradeDate()`：

    * 调用 `https://www.cnindex.com.cn/index/running?type=1` 获取 `peDynamic`；

    * 调用 `https://www.cnindex.com.cn/market/market/getMarketDay?codesValue=980081` 获取 `lastMarketDay`；

    * 输出 `{ tradeDate, pe, source, fetchedAt }`。

  * 新增 `load980081HistoricalPeBaseline()`（通过 `runAkshare` 调 Python 子命令读取 xlsx）：

    * 自动识别日期列候选：`trade_date/date/日期`；

    * 自动识别PE列候选：`PE-TTM-S/PE-TTM/pe_ttm`；

    * 产出 `Map<trade_date, pe>`。

  * 新增 `merge980081PeSeries()`：

    * 先装载历史基线；

    * 再叠加官网最新快照；

    * 同日冲突按你的决策“新值覆盖历史”；

    * 记录 `notes`（基线覆盖、覆盖日期、来源、冲突次数）。

  * 将 `980081` 的 `peSource` 分支从 `public_api_then_etf` 切为“baseline+cnindex\_daily”。
