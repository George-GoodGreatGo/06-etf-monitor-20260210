# 图表稳定性优先精简评估 Spec

## Why
当前低波/价值副图开关问题已修复，但代码中仍存在可精简空间。需要在不破坏稳定性的前提下，明确哪些项适合实施、哪些项应暂缓，并给出分批策略。

## What Changes
- 评估四类精简候选（补偿队列、可见性快照、重复工具函数、effect 收敛）的稳定性风险
- 给出“可立即实施 / 需灰度实施 / 暂不建议实施”的分级结论
- 为可实施项定义最小验收门槛与回归要求
- **BREAKING**: 无

## Impact
- Affected specs: `fix-lowvol-valuetiming-subchart-toggle-sync`
- Affected code:
  - `src/components/charts/LowVolOpportunityChart.tsx`
  - `src/components/charts/MarketLiquidityChart.tsx`
  - （可选）新增图表共享 util/hook 文件

## 评估结论（Tasks 1-4）
### 四类候选项稳定性分级
- 候选A（补偿重放队列收敛为一次性重放）：`P2暂缓`
  - 结论：当前不建议从多层补偿直接收敛为单次重放。
  - 原因：现有 fix spec 仍要求“首轮开关时序补偿”“补偿状态生命周期隔离”，直接收敛会放大首轮 range 不可用/尺寸未稳的失败风险。
  - 触发条件：具备可重复自动化回归（首次开关、多轮开关、奇偶次场景）后再进入专项重构。
- 候选B（prevPaneVisible 快照简化为统一 rebuild + sync）：`P1条件实施`
  - 结论：可以做，但仅限“保留快照语义 + 统一重建入口”的轻量收敛，不做语义删除。
  - 前置条件：先补齐开关序列回归用例，并确保“联动集合确定性”与“数据展示不受联动失败影响”可验证。
  - 验收门槛：连续三轮开关无空白、首轮重开可见、TIPS/crosshair 持续更新。
- 候选C（重复工具函数抽取共享 util/hook）：`P0可立即实施`
  - 结论：优先落地，属于行为等价重构，风险最低。
  - 实施范围：仅抽取重复的 range/crosshair 同步保护、实例可用性判断、空值守卫等通用逻辑；不改变调用时序与状态机。
  - 验收门槛：lint/check 通过，且低波与价值副图开关专项回归通过。
- 候选D（effect 分散触发合并）：`P2暂缓`
  - 结论：当前不具备合并时机。
  - 原因：effect 大重排会同时影响补偿时序、联动锁、重建节奏，和 fix spec 的稳定性优先策略冲突风险高。
  - 触发条件：完成阶段化自动化验证后，以“单模块、可回滚”方式灰度推进。

### P0/P1/P2 实施顺序（含门槛）
- P0（可立即实施）：候选C（共享 util/hook 抽取，行为等价）
- P1（条件实施）：候选B（统一 rebuild + sync 入口，但保留快照语义）
- P2（暂缓）：候选A、候选D（涉及时序重构与 effect 大重排）

### 最小实施建议（分阶段）
- 第一阶段（立即）：仅执行候选C，并允许对局部入口做轻量收敛（不改变时序语义）。
- 第二阶段（条件）：在专项回归自动化补强后，再评估候选B；候选A/D 继续后置。

### 与现有修复 spec 一致性校验
- 本结论不否定也不弱化 `fix-lowvol-valuetiming-subchart-toggle-sync` 中的关键要求：首次重开一致性、多次开关一致性、数据常驻与显示解耦、补偿状态生命周期隔离。
- 本结论仅对“重构优先级与闸门”做分级，不变更既有修复行为基线，因此与现有 fix spec 不冲突。

## ADDED Requirements
### Requirement: 精简项稳定性分级
系统 SHALL 输出候选精简项的稳定性分级，并提供每项的实施前提与回滚触发条件。

#### Scenario: 评估输出
- **WHEN** 完成代码复盘
- **THEN** 对每个候选项给出 `P0可实施 / P1条件实施 / P2暂缓` 结论
- **AND** 给出对应风险说明与验证门槛

### Requirement: 低风险项优先落地策略
系统 SHALL 对低风险项定义直接落地路径，并保证行为等价。

#### Scenario: 低风险项实施
- **WHEN** 选择 `P0可实施` 项
- **THEN** 仅做行为等价重构，不改变用户可见交互
- **AND** 回归后必须通过 lint/check 与开关联动专项验证

## MODIFIED Requirements
### Requirement: 副图开关联动修复后的维护策略
在既有修复基础上，系统 SHALL 采用“稳定性优先”的精简策略：先抽公共工具、再收敛局部状态；高风险的 effect 大重排需后置。

#### Scenario: 高风险改动闸门
- **WHEN** 某精简项涉及联动时序重构（例如大规模 effect 合并）
- **THEN** 必须先通过对照验证与回滚预案评审后再实施

## REMOVED Requirements
### Requirement: 无
**Reason**: 本次为评估与分批策略定义，不移除既有能力
**Migration**: 不涉及迁移
