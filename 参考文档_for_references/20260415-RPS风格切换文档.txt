## 1. 项目概述 (Project Overview)
本项目旨在开发一套**“0 维护、高可用、100% 规则驱动”**的系统性量化监控后端与展示面板。系统专为“哑铃型（防守+进攻）”资产配置策略设计，通过追踪宽基与行业 ETF 的相对强弱指数（RPS），实时捕捉市场资金风格的切换（如价值与成长的轮动）。系统部署在云端，实现每日数据的自动化 ETL（提取、转换、加载），并严格输出剥离了人为情绪的仓位管理指令。

## 2. 用户目标与业务场景 (User Goals & Scenarios)
* **消除情绪干扰**：全职系统性交易者在盘中容易受随机波动影响。本系统在盘后（20:30）提供绝对客观的计算结果，直接生成次日交易计划。
* **杜绝“假信号”**：彻底解决因 ETF 历史分红除息导致的量价指标失真问题。
* **自动化风控纪律**：系统硬性植入单一资产最高 **33%** 的仓位上限限制，防止在单一主线上暴露过多风险。
* **零运维成本与完美容灾**：依托 GitHub Actions 和云数据库，开发者无需维护本地服务器。当外部 API 数据源宕机时，系统能平滑降级（静默回退读取前一日备份），保证前端看板持续运作，不中断复盘流程。

## 3. 数据源与底层口径 (Data Sources)
* **获取接口**：优先使用开源免费的金融数据 API（如 Python 环境下的 `AkShare`、`Tushare` 或 `yfinance`）。
* **时间窗口 (🔴 核心范围)**：自 **2016-01-01** 至今的全量历史日线数据。
* **标的池 (Ticker List)**：
    * **防守基准（分母）**：`515080.SH` (中证红利 ETF)
    * **进攻观测矩阵（分子）**：
        * `159915.SZ` (创业板指 ETF)
        * `588000.SH` (科创50 ETF)
        * `513180.SH` (恒生科技 ETF)
        * `510300.SH` (沪深300 ETF - 作为宽基对照)
* **复权规则 (🔴 强制约束)**：必须指定获取**前复权 (Forward Adjusted, qfq)** 数据。绝不允许使用原始数据或后复权数据。

## 4. 核心计算与业务逻辑 (Calculation Logic)
所有的计算均以 `515080` (中证红利) 为基准底仓，逐一计算各个进攻分子的相对表现：

1. **RPS 基础比值 (Raw Ratio)**：
   $$RPS_t = \frac{Price_{Target}}{Price_{Benchmark}}$$
   *(即：标的前复权收盘价 / 中证红利前复权收盘价)*
2. **趋势平滑 (MA50)**：
   对 $RPS_t$ 序列计算过去 50 个交易日的简单移动平均线（SMA）。
3. **偏离度/动能得分 (Momentum Score)**：
   $$Score = (\frac{RPS_t}{MA_{50}} - 1) \times 100\%$$
4. **状态判定引擎 (核心风控)**：
    * **全面防守 (Risk-Off)**：若所有分子的 Score 均 < 0。系统指令：清空进攻仓位（0%），全量退守红利底仓。
    * **全面进攻 (Risk-On)**：若存在分子的 Score > 0。选取分数最高的标的为【主攻方向】。系统指令：将主攻方向仓位提升至最高 33%，剩余资金保留在底仓。

## 5. 数据更新与容灾策略 (Update & Fallback Strategy)
系统采用双表结构部署在 Supabase (PostgreSQL) 上：
1. `etf_historical_data`（主表）：存储 2016 年至今的全量 K 线数据，需建立 `(ticker, trade_date)` 唯一约束索引。
2. `system_backups`（备份表）：存储每次计算成功后的 JSON 快照。

* **全量覆写机制 (防复权断层)**：每日北京时间 20:30 由 GitHub Actions 触发。脚本不采用“增量更新”，而是**强制全量拉取过去 10 年的数据并覆盖写入** (使用 `UPSERT` 语法)。
* **滚动备份策略**：将包含完整分析结论的数据存入备份表，并按时间戳清理，**永远只保留最近 5 次的成功备份**。
* **静默回退机制 (容灾)**：当捕获到外部 API 宕机、网络超时或数据为空时，脚本 Catch 住异常，停止主表写库，直接从备份表中提取 `T-1` 的数据生成结果。注入 `"is_fallback": true` 标识，确保前端照常渲染。

## 6. 前端呈现思路与内容架构 (Frontend Presentation)
前端仅作为只读看板，直接通过 Supabase Client 读取数据：
* **顶部：核心决策看板 (Executive Summary)**
    * 醒目的状态指示灯（🟢 进攻模式 / 🔴 防守模式）。
    * **大字报式输出最终交易指令**（例如：“当前主攻：科创50 | 建议仓位：33% | 回退状态：正常”）。
* **中部：RPS 动能矩阵表 (Data Matrix)**
    * 表格展示当日 4 个分子的截面数据。包含：标的名称、当前 RPS 比值、50 日均线值、动能得分（按高低排序）、趋势状态。
* **底部：可视化图表 (Visualization)**
    * 绘制 4 条进攻资产相对于红利的 RPS 历史曲线及 50 日均线。提供时间缩放功能，方便复核底背离等 Wyckoff 结构。

## 7. 🚨 开发与实战容易掉坑的地方 (Pitfalls & Gotchas)
请开发者务必仔细阅读，规避以下致命问题：
1. **复权数据“部分更新”陷阱 (致命级)**：由于前复权是动态调整的，一旦 ETF 分红，历史 10 年的前复权价格都会下调。如果只做“增量更新”（只拉今天的数据），历史数据和今天数据会产生物理断层，触发虚假的暴跌或突破信号。**必须执行全量覆写！**
2. **不复权或后复权陷阱 (逻辑级)**：不复权会导致除息日价格暴跌；后复权会导致早期数据变成天文数字，比值失去直观意义且引发浮点数精度丢失。
3. **单点故障与脆弱性陷阱 (工程级)**：免费 API 极不稳定。脚本不加 try-catch 会导致行动流崩溃，复盘面板白屏。**必须严格执行静默回退机制！**
4. **基准分母的纯度陷阱 (策略级)**：绝不能用沪深300作分母（其包含大量成长股会引发风格对冲钝化）。必须以中证红利作唯一防守基准，保持“矛与盾”的极致对立。
